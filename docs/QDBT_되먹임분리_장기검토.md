# QDBT — 되먹임 분리 방식 장기 아키텍처 검토

> 대상: 개발 실행 로드맵 T4 (되먹임 분리) 방식 결정
> 목적: 물리적 분리(별도 테이블) vs 논리적 분리(동결 범위 축소)를 **장기 관점**에서 평가하고 권고.
> 결론: **물리적 분리(별도 매핑 테이블)를 권고.** 근거는 비교 결과의 버전 종속성·이미 존재하는 매칭 분산·소유권 명시 필요성.

---

## 1. 두 방식의 정의

### 논리적 분리 (동결 범위 축소)
- submission_items에 견적 원본 + 비교 결과가 **계속 공존**.
- 동결 대상을 "견적 원본 필드(품명·규격·수량·단가·금액)"로 한정.
- catalog_item_id·match_status·match_confidence·match_note는 동결에서 제외(비교 WS가 자유롭게 씀).
- 스키마 변경·마이그레이션 없음.

### 물리적 분리 (별도 매핑 테이블)
- submission_items = **견적 원본만**.
- 신규 테이블(예: `item_match`) = 비교 결과(item_id, catalog_item_id, match_status, match_confidence, match_note).
- 소유권이 스키마에 명시: submission_items=병합 WS, item_match=비교 WS.

---

## 2. 핵심 발견 — 결정을 좌우하는 세 사실 (코드 확인)

### 발견 1: 매칭 정보가 이미 두 곳에 분산 저장돼 있다
- `submission_items.catalog_item_id` (어느 카탈로그 품목에 연결)
- `catalog_cluster_members` (cluster_id ↔ item_id 매핑)

→ 매칭이 **이미 정규화되지 않은 상태**로 두 곳에 흩어져 있다. 논리적 분리는 이 분산을 그대로 방치하고, 물리적 분리는 이를 정리할 기회다.

### 발견 2: 비교 결과는 버전 종속적이다
확정 v1의 클러스터링과 v2의 클러스터링은 **다를 수 있다**(항목이 바뀌면 매칭도 바뀜).
- 비교 결과가 submission_items에 있으면 → "이 catalog_item_id는 어느 버전의 매칭인가?"가 **모호**.
- submission_items는 현재 작업본(draft)인데, 매칭 결과가 얹혀 있으면 버전 경계와 충돌.

→ 비교 결과는 본질적으로 "버전 × 항목"의 함수다. 별도 테이블이면 버전 차원을 자연히 표현(item_match에 version 추가 가능). 동결 범위 축소로는 버전 종속성을 표현할 수단이 없다.

### 발견 3: catalog_item_id는 143곳에서 참조된다
- 대부분은 **읽기**(JOIN, 조회). 쓰기(되먹임)는 소수(clusterer 1117행 등).
- 물리적 분리 시 읽기 143곳은 JOIN 경로만 바꾸면 됨(값 자체는 동일 위치서 조회 가능하게 뷰·JOIN 제공).
- 즉 143곳이 모두 수정 대상은 아니며, 대부분 JOIN 한 줄 변경 또는 호환 뷰로 흡수 가능.

## 3. 장기 관점 다축 비교

| 평가 축 | 논리적 분리 (동결 범위 축소) | 물리적 분리 (별도 테이블) |
|---------|------------------------------|---------------------------|
| **초기 비용** | ★ 낮음 (스키마 무변경) | 중 (신규 테이블·마이그레이션) |
| **소유권 명확성** | ✗ 코드에만 존재(스키마 불투명) | ★ 스키마에 명시 |
| **버전 종속성 표현** | ✗ 불가(버전 차원 없음) | ★ 자연(version 컬럼) |
| **동결 로직 단순성** | ✗ 필드별 화이트리스트 관리 | ★ 테이블 단위 통째 동결 |
| **매칭 분산 해소** | ✗ 방치(2곳 분산 유지) | ★ 정리 기회 |
| **확장성**(매칭 이력·다중 클러스터) | ✗ submission_items 비대화 | ★ 매핑 테이블 확장 |
| **진화 아키텍처 정합** | 중 (물리 분리 유보와 형식상 부합) | ★ "필요시 물리 분리 승격"의 첫 실현 |
| **디버깅·추적** | ✗ 원본/결과 혼재 | ★ 관심사별 격리 |

**단기 1승(초기 비용) vs 장기 7승(물리적 분리).**

## 4. 장기적 권고 — 물리적 분리

### 4.1 결론
**물리적 분리(별도 매핑 테이블)를 권고한다.** 논리적 분리는 초기 비용만 낮을 뿐, 장기적으로 기술 부채가 된다.

### 4.2 논리적 분리가 부채가 되는 이유
1. **버전 종속성을 우회할 수 없다**: 버전 관리(D3)가 도입되면 "어느 버전의 매칭인가"를 반드시 표현해야 하는데, submission_items에 얹힌 단일 catalog_item_id로는 불가능. 결국 나중에 물리적 분리로 가야 하며, 그때는 데이터가 더 쌓여 마이그레이션이 더 어렵다.
2. **동결 화이트리스트의 복잡도가 누적된다**: "이 필드는 동결, 저 필드는 아님"을 코드 전반에서 관리해야. 필드가 늘 때마다 화이트리스트 갱신. 실수 시 동결 위반.
3. **매칭 분산을 고착시킨다**: 이미 2곳(submission_items·cluster_members)에 흩어진 매칭을 정리하지 않고 방치.

### 4.3 물리적 분리의 장기 이점
1. **소유권이 스키마에 새겨진다**: 병합 WS는 submission_items만, 비교 WS는 item_match만 쓴다. 앞서 논의한 "소유권 규칙"이 코드 규율이 아니라 구조로 강제된다.
2. **버전 종속성을 자연히 표현**: item_match에 version(또는 snapshot_id) 차원을 두면, 버전별 매칭 이력이 데이터 모델에 담긴다.
3. **동결이 단순·안전**: submission_items 테이블 통째 동결. 화이트리스트 불필요.
4. **진화 아키텍처의 첫 물리적 분리**: "관심사 분리, 필요 증명 시 물리 분리 승격"에서 버전 종속성이 그 필요를 증명. item_match가 첫 승격 사례.

## 5. 물리적 분리 설계 (권고안)

### 5.1 신규 테이블
```
item_match  (비교 WS 소유)
  item_id          TEXT   -- submission_items.item_id (FK)
  catalog_item_id  TEXT   -- 연결된 카탈로그 품목
  match_status     TEXT   -- pending | suggested | confirmed | unmatched
  match_confidence REAL
  match_note       TEXT
  version          INTEGER DEFAULT NULL  -- 버전 종속 매칭(D3 대비, 초기 NULL)
  updated_at       TIMESTAMP
  PRIMARY KEY (item_id, version)   -- 버전별 매칭 허용
```
- 초기(D3 이전): version=NULL로 현재 매칭만. D3 도입 시 버전별 확장.
- submission_items에서 catalog_item_id·match_* 4필드 제거(또는 뷰 호환 기간 후).

### 5.2 마이그레이션 전략 (무손상·점진)
1. **테이블 생성 + 데이터 이관**: submission_items의 매칭 4필드를 item_match로 복사(idempotent).
2. **호환 뷰 제공**: 기존 143곳 읽기를 위해 `submission_items_with_match` 뷰(JOIN) 임시 제공 → 코드 점진 이행.
3. **쓰기 경로 전환**: 되먹임 쓰기(clusterer 등)를 item_match로. submission_items 매칭 필드 쓰기 중단.
4. **읽기 경로 전환**: 143곳을 JOIN 또는 뷰로 점진 이행.
5. **구필드 제거**: 모든 이행 후 submission_items에서 매칭 4필드 DROP(선택, 안전 후).

→ 각 단계가 독립·되돌림 가능. 급격한 전환 없음.

### 5.3 이점 실현
- 이 설계 후 submission_items는 **순수 견적 원본** → 확정 시 테이블 통째 동결(단순).
- item_match는 비교 WS가 자유 갱신 → 되먹임·재매칭이 원본 불변.
- 버전 관리(D3) 도입 시 version 차원 활성화 → 버전별 매칭 이력.

## 6. 리스크와 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 143곳 읽기 이행 부담 | 작업량 | 호환 뷰로 점진 이행(급격 전환 회피) |
| 마이그레이션 중 정합성 | 데이터 | idempotent 이관·이중 기록 기간·검증 |
| JOIN 성능 | 조회 속도 | item_match(item_id) 인덱스, 필요 시 뷰 캐시 |
| price_history·cluster_members 연동 | 참조 | 이 둘도 item_match 경유로 일관(정리 기회) |

## 7. 권고 요약

- **물리적 분리 채택.** 단기 비용(마이그레이션)은 있으나, 버전 종속성·소유권 명시·동결 단순성·확장성에서 장기 우위.
- **핵심 근거**: 비교 결과는 버전 종속적이며, 논리적 분리로는 이를 표현할 수 없어 결국 물리적 분리로 가야 한다. 늦출수록 데이터가 쌓여 비용이 커진다.
- **실행**: 호환 뷰 기반 점진 이행으로 143곳 부담을 흡수. 각 단계 독립·되돌림 가능.
- **정합**: 이 결정이 감사 문제 1·4·5를 해소하고, 진화 아키텍처의 "필요 증명 시 물리 분리 승격"을 실현한다.

## 8. 미결 사항 (착수 전 확정)

- item_match의 version 차원을 초기부터 둘지, D3 도입 시 추가할지
- 호환 뷰 유지 기간(구필드 DROP 시점)
- price_history·cluster_members의 매칭 참조를 item_match로 일원화할 범위
- 신규 테이블 명칭(item_match vs item_catalog_link)
