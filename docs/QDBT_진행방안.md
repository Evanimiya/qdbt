# QDBT — 다음 단계 진행 방안

> 기준: 즉시 그룹(T1·T2·T2b) 완료, 되먹임 분리(T4) 완료 시점
> 목적: 남은 작업의 진행 경로를 실사용 가치·의존성·규모로 분석하고 권고.
> 방법: 코드 실측 기반. 세 경로 비교 후 단일 권고 + 병행안.

---

## 0. 현재 위치

```
완료: C1~C6(통화·환율·도메인·item_match) · T1·T2·T2b(즉시) · T4(되먹임 분리)
남음: T3(용어) · T5(합계모듈) │ T6(다중시트)·T7(N레벨연계)·T8(묶음펼치기)
      │ T9~T12(버전관리) │ T13·T14(UI)
```

핵심 경로(로드맵): T3 → **T4(완료)** → T9 → T10 → T11 → T12
병렬 축: T5 → T6 → T7 → T8

**T4가 이미 완료**되어, 버전 관리(T9~) 선결의 절반이 갖춰짐. 병합 기능 축(T5~T8)은 아직 미착수.

## 1. 후보 작업 실측

| 작업 | 규모(실측) | 실사용 임팩트 | 위험 | 준비도 |
|------|-----------|--------------|------|--------|
| **T5 합계검증모듈** | 합계 로직 22곳 분산 | 간접(품질) | 낮음 | 부분 존재(recompute·불변식) |
| **T6 다중시트추출** | 1함수+2저장+UI | **높음(실버그)** | 중 | 설계·목업 완비 |
| **T7 N레벨연계** | 신규 UI+연계로직 | 높음 | 높음 | 목업·설계 확정 |
| **T3 용어표준화** | accept 39·confirm 24 | 낮음(일관성) | 코드까지 시 중 | 결정 필요 |
| **T9 상태모델** | merge_status 신설 | 중(프로세스) | 중 | T4 완료로 절반 |

**핵심 관찰**:
- **T6는 실사용 버그**("여러 시트 추출 시 마지막만") — 사용자가 실제 겪음. 근본원인(삭제-덮어씀) 명확, 범위 좁음.
- T5는 22곳 분산 — 통합 가치 크나 그 자체로 체감 변화는 적음. 단 T6/T7의 소계 검증 토대.
- T3 코드 표준화는 63곳 영향 — 문서만이면 저위험, 코드까지면 중위험.

## 2. 세 진행 경로

### 경로 A — 실사용 임팩트 우선 (병합 기능)
```
T5(합계모듈) → T6(다중시트) → T7(N레벨연계) → T8(묶음펼치기)
```
- **논리**: 사용자가 실제 겪는 문제(다중 시트)를 최단 해결. 목업·설계 완비.
- **장점**: 즉각 체감. 방향 합의 완료. T5가 T6/T7 소계 검증 토대로 자연 선행.
- **단점**: 버전 관리(T9~) 지연. T7은 고난도.
- **기간감**: T5(소) → T6(중) → T7(대) → T8(중).

### 경로 B — 구조 정리 우선
```
T3(용어) → T5(합계모듈) → [이후 병합 or 버전]
```
- **논리**: 이후 모든 작업의 토대(용어·합계)를 먼저 정리.
- **장점**: 저위험. 이후 작업의 일관성·품질 향상.
- **단점**: 사용자 체감 변화 적음. 실버그(T6) 해결 지연.
- **적합**: 당장 급한 기능이 없고 기반을 다지고 싶을 때.

### 경로 C — 버전 관리 조기 착수
```
T9(상태모델) → T10(동결) → T11(확정루프) → T12(스냅샷)
```
- **논리**: T4(되먹임 분리) 완료로 선결 절반 갖춰짐. 확정·버전은 큰 가치.
- **장점**: 데이터 신뢰성·감사 추적. 되먹임 분리 효과 실현.
- **단점**: 병합 기능(T6~) 미성숙 상태에서 버전만 앞서면 실효 제한. T3(용어) 선결 권장.
- **적합**: 확정·이력이 당면 요구일 때.

## 3. 권고 — 경로 A (실사용 임팩트 우선), T5부터

### 3.1 권고 이유
1. **실버그 해결이 최우선 가치**: T6는 사용자가 실제 겪는 "다중 시트 마지막만 추출". 근본원인이 명확하고(삭제-덮어씀) 범위가 좁아, 확실한 임팩트를 빠르게 낸다.
2. **설계·목업 완비**: T6·T7은 이미 설계서·라이브목업으로 방향 합의됨. 재논의 없이 구현 착수 가능.
3. **T5가 자연 선행**: 다중 시트·N레벨은 소계 검증이 핵심인데, T5(합계 모듈)가 그 토대. T5 먼저 하면 T6/T7이 그 위에 얹힌다. T5는 저위험·독립.
4. **T4 활용**: 되먹임 분리 완료로, 병합 기능이 비교(클러스터링)와 깔끔히 분리됨. 지금이 병합 기능 확장의 적기.

### 3.2 권고 순서
```
1) T5 합계 검증 공통 모듈       [저위험·토대]
   · 4종 불변식(공급가액=트리=라인, Σ잎=묶음, Σ배치=노드소계, amount=단가×수량) 통합
   · ④는 이미 처리 → 나머지 통합. 단일 검증 함수로.
2) T6 다중 시트 누적 추출        [실버그 해결]
   · 삭제 1회 + 시트별 추출·누적 삽입. map_config v2.
   · 근본원인 직접 해소. 백엔드 우선, UI 최소.
3) T7 N레벨 시트 연계           [고가치·고난도]
   · 레벨 지정(추론+수정) + 드래그 연계(상하관계·방향자유·건너뛰기) + 소계 검증(T5 재사용).
   · 목업 그대로 구현.
4) T8 묶음 펼치기 (여력 시)
```

### 3.3 T3(용어)·T9(버전)는?
- **T3**: 경로 A와 **병행**. 문서 표준화는 지금 반영, 코드 변수·함수명은 T6~ 진행 중 접촉하는 파일에서 점진 정리. 별도 스프린트 불필요.
- **T9~(버전)**: 병합 기능(T6·T7) 성숙 후 착수. T4 완료로 준비됐으나, 병합이 실효를 뒷받침해야 의미. 경로 A 완료 후 자연히 다음.

## 4. 즉시 착수안 — T5 합계 검증 공통 모듈

### 4.1 목표
22곳에 분산된 합계·소계 로직을 단일 검증 모듈로. 이후 T6·T7이 재사용.

### 4.2 통합 대상 4종 불변식
```
① 공급가액 = 트리 합 = 라인 합    (recompute_subtotal — 존재)
② Σ잎 == 묶음 금액               (묶음펼치기)
③ Σ배치 == 노드 소계            (다중시트·N레벨)
④ amount == 단가 × 수량          (환율 — 이미 처리)
```

### 4.3 설계 방향
- `validate_totals(items, mode)` 형태의 단일 진입점.
- 각 불변식을 파라미터/모드로. 허용 오차(반올림·부가세) 인자.
- 반환: 정합 여부 + 불일치 상세(어느 노드, 차액).
- T6/T7이 시트·노드 병합 후 이 함수로 검증.

### 4.4 규모·위험
- 저위험: 기존 recompute_subtotal 로직 재활용 + 검증 함수 신설.
- 스키마 무변경. 독립적.
