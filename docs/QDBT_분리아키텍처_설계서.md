# QDBT — 병합·비교 워크스페이스 분리 아키텍처 설계서

> 대상 버전: v0.10.0 (구조 개편) · 작성 기준: v0.9.7 코드
> 상태: 아키텍처 설계 확정, 구현 착수 전
> 결정: **방식 B — 하나의 앱, 두 워크스페이스(논리 분리)** · 경계면 = **정규화된 견적서(submission done 상태)**

---

## 1. 배경과 문제의식

지금까지 QDBT는 "타 업체 견적서 비교"를 중심으로 설계됐다. 그러나 실무에서 **견적서 내용 병합**(한 업체의 분산된 견적서를 하나의 정규화된 트리로 조립)이 비교 못지않게, 때로 더 중요하다는 인식에 이르렀다.

**비교와 병합은 본질이 다른 작업이다.**

| 축 | 병합 (Merge) | 비교 (Compare) |
|----|------|------|
| 성격 | 구성(construction) | 분석(analysis) |
| 방향 | 쓰기 중심 | 읽기 중심 |
| 대상 | 한 업체 견적서 하나 | 여러 업체 견적서 |
| 핵심 상호작용 | 드래그앤드랍·트리 조립·항목 배치 | 표 비교·클러스터링·가격이력 |
| 상태 | 편집 상태 많음(배치 이력) | 조회 상태 위주 |

두 작업을 한 화면·한 모듈에 섞으면 병합의 복잡한 편집 UI가 비교의 분석 화면을 오염시킨다. 실제로 현재 `compare/bid.html`이 비교표에 클러스터 이동·항목 선택·드래그가 얽혀 비대해지고 있다.

---

## 2. 핵심 근거 — 데이터 소유가 이미 분리되어 있다

현행 15개 테이블은 두 관심사로 자연히 갈린다. 결정적으로 **의존이 단방향**이다: 비교 영역이 병합 영역을 읽기만 하고, 역방향 의존은 없다.

### 2.1 테이블 소유권

**병합 소유 (견적서를 만드는 데이터) — 쓰기 주체 = 병합 WS**
`projects` · `bids` · `submissions` · `submission_items`
(트리·항목·통화·환율·nego·compare_units·map_config)

**비교·축적 소유 (견적서를 견주고 쌓는 데이터) — 쓰기 주체 = 비교 WS**
`catalog_clusters` · `catalog_cluster_members` · `catalog_items` · `catalog_categories` · `price_history` · `bid_watchlist` · `catalog_suggestions`

**공유 (양 WS 공통 참조, 읽기 위주)**
`users`(인증) · `domains`(도메인 마스터) · project/bid 기준정보

### 2.2 의존 방향 (검증됨)

```
[병합 WS] submission_items  ──(읽기)──▶  [비교 WS] catalog_cluster_members
                                            (catalog_item_id = item_id)
병합은 비교를 모른다.  비교만 병합 결과를 참조한다.  → 단방향 = 분리 가능
```

## 3. 아키텍처 결정 — 방식 B

### 3.1 결정 요지
하나의 Flask 앱 안에서 **병합 워크스페이스(/merge)**와 **비교 워크스페이스(/compare)**를 명확히 가른다. 스키마·배포·인증은 하나로 유지하되, 진입점·네비게이션·화면·블루프린트를 두 앱처럼 분리한다.

### 3.2 방식 B 선택 근거
- **운영 제약 부합**: 폐쇄망 VDI·zip 패치·단일 SQLite에서 완전 별도 앱(방식 A)의 이중 배포·프로세스 간 SQLite 잠금 부담이 없다.
- **분리 실익 확보**: 병합의 복잡한 편집 경험을 비교와 격리해 집중 개발·독립 발전 가능.
- **스키마 유지 요건 부합**: "기본 스키마 유지" 방침과 정합 (공유 DB, 컬럼 재활용).

### 3.3 방식 A 대비 (미채택)
완전 별도 앱은 조직적으로 다른 팀·다른 배포 주기로 갈 때 정당화된다. 현 단계에선 배포·동시성 부담이 실익을 상회하므로 보류. **방식 B는 향후 방식 A로 승격 가능한 구조**로 설계한다(블루프린트 경계가 곧 미래 앱 경계).

## 4. 경계면 — 정규화된 견적서 (핸드오프 게이트)

### 4.1 경계 정의
두 WS가 주고받는 유일한 지점은 **정규화된 견적서**다. 상태로는 `submissions.extraction_status = 'done'`.

```
[병합 WS]  추출 → 트리 조립 → 항목 배치 → 확정        [비교 WS]
   ────────────────────────────────▶  done  ──────────────────▶
   (submission_items 트리 완성)      게이트     클러스터링·비교·축적
```

- **병합 WS 산출물** = 확정된 단일 견적서(완성된 submission_items 트리)
- **비교 WS 입력** = done 상태의 여러 submission
- `done`이 **핸드오프 게이트**: done 이전엔 병합 WS만, done 이후엔 비교 WS가 참조

### 4.2 게이트 규칙
- 병합 WS: done 이전 submission을 자유 편집(재추출·재배치·환율수정)
- 비교 WS: done submission을 읽어 클러스터링. **원본 트리는 수정하지 않음**(카탈로그·클러스터만 생성)
- done 이후 병합 WS가 재편집하면 → 연결된 클러스터 무효화 신호(재클러스터링 유도)

## 5. 워크스페이스 구성

### 5.1 병합 워크스페이스 (/merge)

**책임**: 파일 업로드 → 추출 → 트리 조립 → 항목 배치 → 통화·환율 확정 → done

**포함 블루프린트/기능**:
- `submissions`(26 라우트): 업로드·열매핑·추출·통화환율·nego
- 신규: 다중 탭 통합 추출, 트리·세부 분리 조립, **드래그앤드랍 항목 배치**
- projects·bids의 견적서 등록 부분

**핵심 화면**: 열 매핑, 탭 통합, 트리 조립(드래그앤드랍), 통화·환율 패널, 제출서 상세

### 5.2 비교 워크스페이스 (/compare)

**책임**: done 견적서들 → 클러스터링 → 업체 비교 → 카탈로그·가격이력 축적

**포함 블루프린트/기능**:
- `compare`(24 라우트): 비교표·클러스터링·클러스터 편집
- `catalog`(30 라우트): 카탈로그 원장·분류·도메인·가격이력
- `bid_watchlist`·suggestions

**핵심 화면**: 업체별 비교, 클러스터 관리, 카탈로그, 가격이력

### 5.3 공유 레이어

두 WS가 공통으로 쓰는 횡단 요소:
- **인증**(`auth`·`profile`): 로그인·권한·API 키
- **도메인·분류 마스터**(`domains`·`catalog_categories`): 기준정보 (단, 편집은 비교 WS/admin)
- **관리자**(`admin`): 사용자·시스템 설정
- **공통 유틸**: 통화 필터(cursym), 트리 유틸, 경로 정규화

## 6. 공통 인프라 — 두 기능의 구조적 동형 활용

병합의 트리 조립과 비교의 묶음 펼치기는 **구조적으로 동형**이다(노드-잎 귀속 + 합계 검증 + 자동/수동 보정). 분리 설계 시 공통 모듈로 추출해 양쪽이 재사용한다.

| 공통 부품 | 병합 WS 사용 | 비교 WS 사용 |
|-----------|------|------|
| 노드-잎 귀속 로직 | 세부 항목 → 트리 노드 배치 | 잎 → 클러스터 배치 |
| 합계 검증기 | Σ배치 == 노드 소계 | Σ잎 == 묶음 금액 |
| 드래그앤드랍 UI | 항목 → 트리 노드 | 잎 → 클러스터 재배치 |
| 이름 매칭(표기편차 흡수) | 탭명 ↔ 노드명 | 잎 완전경로 ↔ compare_units |

→ **공통 모듈 위치**: 공유 레이어. 먼저 구현하는 WS가 인프라를 제공, 나중 WS가 재사용.

## 7. 화면·네비게이션 설계

### 7.1 최상위 진입
- 홈에서 두 워크스페이스를 명확히 제시: **[견적서 병합]** / **[견적서 비교·축적]**
- 상단 네비에 현재 WS 표시, WS 간 전환 명시

### 7.2 흐름 연결
```
병합 WS: 프로젝트 > 입찰 > 견적서 업로드·조립 → [확정]
              │  확정된 견적서
              ▼
비교 WS: 입찰 > 업체 비교 > 클러스터링 > 카탈로그·이력
```
- 병합 WS에서 "확정" 시 "비교 WS로 이동" 안내
- 비교 WS에서 "이 견적서 편집" 시 병합 WS로 돌아감(done 해제 경고)

## 8. 마이그레이션·구현 전략 (점진적, 무중단)

기존 기능을 깨지 않고 단계적으로 분리한다. **스키마 변경 없음**(블루프린트·URL·화면 재구성 중심).

**1단계 — 논리 경계 정의**: 블루프린트를 두 그룹으로 명명·정리(merge_bp군 / compare_bp군). URL prefix 정비(/merge, /compare). 기능 이동 없이 분류만.

**2단계 — 공유 레이어 추출**: 인증·도메인·통화유틸·트리유틸을 공통 모듈로. 노드-잎 귀속·합계 검증·드래그앤드랍을 공통 부품으로 설계(6절).

**3단계 — 병합 WS 강화**: 다중 탭 통합·트리 조립·드래그앤드랍 배치 구현(공통 부품 위에). done 게이트 명확화.

**4단계 — 비교 WS 정리**: compare/bid.html에서 병합성 편집 UI를 병합 WS로 이관. 비교는 분석에 집중.

**5단계 — 네비게이션 통합**: 최상위 WS 선택·전환 UX. 흐름 연결.

각 단계 종료 시 배포·검증·협의(그룹 단위 원칙).

---

## 9. 소유권 규칙 (명문화)

분리의 무결성을 지키는 규칙. 위반 시 데이터 모순 발생.

- `submissions`·`submission_items`: **병합 WS 쓰기**, 비교 WS 읽기 전용
- `catalog_*`·`price_history`: **비교 WS 쓰기**, 병합 WS 미참조
- `domains`·`catalog_categories`(분류 마스터): admin/비교 WS 쓰기, 병합 WS 읽기
- done 게이트: 병합→비교 단방향 핸드오프. done 해제는 병합 WS 권한, 비교 산출물 무효화 동반

---

## 10. 기대 효과

- **집중 개발**: 병합의 드래그앤드랍·트리 조립을 비교와 무관하게 발전
- **UI 정리**: 비교표가 편집 부담을 벗고 분석에 집중
- **재사용**: 노드-잎 귀속·합계 검증·드래그앤드랍 공통 부품 일원화
- **확장성**: 향후 방식 A(완전 별도 앱) 승격 시 블루프린트 경계가 곧 앱 경계
- **관심사 명확화**: "견적서를 잘 만든다"(병합)와 "견적서를 잘 견준다"(비교)의 분리

## 11. 리스크와 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| done 이후 병합 재편집이 클러스터 무효화 | 비교 결과 불일치 | 재편집 시 연결 클러스터 무효화 신호·재클러스터링 유도 |
| 공유 레이어 비대화 | 분리 의미 희석 | 공유는 인증·마스터·유틸로 최소화, 비즈니스 로직은 각 WS |
| 점진 분리 중 과도기 혼란 | 사용자 흐름 끊김 | 단계별 배포, 기존 URL 호환 유지(리다이렉트) |
| 소유권 규칙 위반 | 데이터 모순 | 규칙 명문화(9절), 쓰기 경로 단일화 |

## 12. 미결 사항 (구현 착수 전 확인)

- done 게이트의 재편집 정책: 재편집 시 클러스터 자동 무효화 vs 경고 후 수동
- 병합 WS의 "확정" 단위: 제출서별 vs 입찰 전체 일괄
- 공유 도메인·분류 마스터의 편집 권한 위치(admin 단독 vs 비교 WS 겸용)
- 향후 방식 A 승격 대비, 공유 DB 접근을 서비스 계층으로 추상화할지
- 네비게이션에서 두 WS를 완전 분리 표시할지, 프로젝트 맥락은 공유할지
