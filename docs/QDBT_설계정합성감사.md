# QDBT — 설계 정합성 감사 보고서

> 작성 기준: v0.9.7 코드 + 본 세션 전체 설계 문서
> 목적: 세션 동안 진화한 여러 설계서가 **서로 정합하는지**, 특히 후반 결정(item_id 동결·self-contained 스냅샷·done 종속 상태)이 전반 설계서(묶음펼치기·다중탭)와 **모순 없는지** 감사.
> 방법: 각 설계서의 핵심 주장을 코드 근거와 대조. 발견된 모순·간극을 심각도순 제시하고 해소 방향 제안.
> 결론: **5개 정합성 문제 발견.** 그중 1개는 종합 명세서 자체의 결함(동결↔되먹임 충돌). 구현 착수 전 반드시 해소.

## 0. 감사 대상 문서

| 문서 | 핵심 주장 |
|------|-----------|
| 종합설계변경명세서 | item_id 동결, self-contained 스냅샷, done 종속 상태 |
| 묶음펼치기 설계서 | 묶음 확정 시 잎 보존(role='leaf', item_id 참조), 펼침 시 잎 재매칭 |

| 진화아키텍처 로드맵(부록 B·C) | 리뷰·확정 프로세스, 스냅샷·취소 |

## 1. 발견된 정합성 문제 (심각도순)

### 문제 4 [치명·명세서 자체 결함] — 동결과 되먹임의 정면 충돌

**모순**:
- 명세서 §1.2(B): `confirmed` 상태에서 submission_items **동결**(변경 금지).
- 실재 코드: 클러스터 확정(accept) 시 되먹임 8곳이 `submission_items.category·catalog_item_id·match_status`를 **수정**(clusterer 1116행 등).

**충돌 구조**:
```
제출서 confirmed (동결) ──▶ 비교 WS에서 클러스터링·클러스터 확정
                              └─▶ submission_items 되먹임 수정 ✗ 동결 위반!
```
비교 WS가 클러스터를 확정하면 confirmed 제출서의 submission_items를 쓴다. 동결이 이를 금지하면 클러스터 확정이 불가능하고, 허용하면 동결이 무의미해진다.

**근본 원인**: 명세서가 "동결"을 도입할 때, 되먹임이 **confirmed 제출서를 대상으로** 일어난다는 사실을 반영하지 못함. DB 검증(직전 세션)이 되먹임의 존재는 밝혔으나, 그것이 동결과 충돌함은 놓침.

**해소 방향 (택1 또는 조합)**:
- **(A) 되먹임을 별도 필드로 분리**: 클러스터 결과(catalog_item_id·match_status)를 submission_items가 아니라 **별도 매핑 테이블**에 저장. submission_items 원본은 진짜 불변. → 되먹임이 동결을 건드리지 않음. (구조 정리, 앞서 "되먹임 인터페이스화"와 연결)
- **(B) 동결 범위 축소**: 동결 대상을 "추출 데이터(트리·금액·수량)"로 한정하고, "클러스터 연결 필드(catalog_item_id·match_status·category)"는 동결에서 제외. → 되먹임 허용하되 핵심 값은 불변.
- **권장**: (A) — 관심사 분리에 부합. submission_items는 순수 견적 데이터, 클러스터 연결은 별도. 이것이 앞선 "되먹임 서비스 함수 수렴"의 자연스러운 귀결.

### 문제 2 [중대] — '확정' 용어의 이중 의미

**모순**: "확정"이 두 설계에서 다른 것을 가리킨다.
- 묶음펼치기: "묶음 확정" = **클러스터 accept**(비교 WS, `accept_cluster_from_compare` 448행)
- 명세서/부록: "확정" = **merge_status=confirmed**(병합 WS, 제출서 단위)

두 확정은 **다른 단계·다른 WS·다른 대상**이다. 문서 간 "확정"이 혼용되면 구현자가 혼동한다.

**해소 방향**: 용어 표준화.
- 제출서 확정(병합) = **"확정"(confirm)**
- 클러스터 확정(비교) = **"클러스터 수락"(accept)** 으로 명칭 분리
- 묶음펼치기의 "묶음 확정 시 잎 보존"은 정확히는 "**클러스터 수락 시** 잎 보존"으로 정정.

### 문제 1 [중대] — 잎 보존(item_id 참조) vs 스냅샷(self-contained)

**모순**:
- 묶음펼치기 §3.1: 잎을 `catalog_cluster_members`에 **item_id 참조**로 보존(role='leaf').
- 명세서 §1.2(A): 스냅샷은 item_id **비참조**(값 사본).

두 "잎 보존"이 저장 방식이 다르다. 클러스터 멤버(item_id 참조)와 확정 스냅샷(값 사본)이 **별개 저장소**인데, 둘의 관계가 미정의.

**핵심 질문**: 펼침용 잎은 어디에 사는가?
- 클러스터 멤버(비교 WS, item_id 참조) — 살아있는 데이터, 재매칭 대상
- 확정 스냅샷(값 사본) — 불변 기록

**해소 방향**: 두 저장소의 역할 분리 명문화.
- **클러스터 멤버(item_id 참조)**: 현재 활성 비교용. confirmed 제출서의 동결된 item_id를 참조하므로 안정(동결이 참조 무결성 보장).
- **스냅샷(값 사본)**: 확정 시점 감사·복원용. 펼침 재매칭에 쓰지 않음.
- → 펼침·재매칭은 **클러스터 멤버**를 쓰고(item_id 참조, 동결로 안정), 스냅샷은 이력 전용. 이원화가 아니라 **역할 분담**으로 정합.
- 단, 이는 문제 4 해소(되먹임 분리)와 연동 — catalog_item_id가 별도 테이블이면 잎 참조도 그곳에.

### 문제 5 [중대] — 잎 재매칭 vs 동결

**모순**:
- 묶음펼치기: 펼침 시 잎 재클러스터링 → `catalog_cluster_members` 변경.
- 명세서: confirmed 제출서 동결.

잎 재매칭이 confirmed 제출서의 클러스터 연결을 바꾸면 동결 위반 우려.

**해소 방향**: 문제 4의 (A)로 자동 해소. 잎 재매칭은 submission_items가 아니라 **클러스터 멤버·매핑 테이블**을 변경하므로, submission_items 원본(동결 대상)은 불변. → 재매칭은 "비교 결과의 갱신"이지 "견적서의 변경"이 아님. 동결과 무관.

### 문제 3 [경미] — 다중탭 통합추출의 draft 제약 미반영

**간극**: 명세서 §3.3은 "통합 추출은 draft에서만(확정 전)"을 추가했으나, 다중탭 설계서 본문에는 이 제약이 **명시되지 않음**.

**해소 방향**: 다중탭 설계서에 "통합 추출은 draft 상태에서만 수행. confirmed는 동결이므로 재추출 불가(취소 후 draft에서)" 명문화.

## 2. 교차 관심사 정합성 (종합)

### 2.1 item_id 생명주기 — 정합 가능 (조건부)

| 사용처 | item_id 취급 | 동결과 정합? |
|--------|-------------|-------------|
| 다중탭 통합추출 | draft에서 재생성 | ✓ (draft만, 문제3 명문화 후) |
| 묶음펼치기 잎 참조 | confirmed 잎 참조 | ✓ (동결로 안정) |
| 스냅샷 | 비참조(값 사본) | ✓ (독립) |
| 되먹임(클러스터 연결) | confirmed 참조·수정 | ✗ → 별도 테이블로(문제4 A) |

→ **문제 4를 (A)로 해소하면 item_id 생명주기 전체가 정합.** 핵심: submission_items 원본은 confirmed에서 불변, 클러스터 연결은 별도 저장소.

### 2.2 합계 불변식 — 공통 체계로 통합 필요

4종의 불변식이 흩어져 있다:
```
① 공급가액 = 트리 = 라인 합    (recompute_subtotal, 기존)
② Σ잎 == 묶음 금액             (묶음펼치기)
③ Σ배치 == 노드 소계          (다중탭)
④ amount == 단가 × 수량        (환율 수정 — 현재 위반, 명세서 §1.1 수정 대상)
```
명세서는 "공통 부품(합계 검증기)"을 주장하나, ④가 위반된 채 배포된 것은 **공통 체계 부재**의 증거다.

**해소 방향**: 단일 합계 검증 모듈로 통합. 모든 기능이 이 모듈을 호출. ④ 수정 시 이 모듈에 amount=단가×수량 규칙을 넣어, 이후 모든 기능이 자동 준수.

### 2.3 상태 모델 — '확정' 용어 정리 후 정합

문제 2 해소(확정=제출서 확정, 수락=클러스터) 후, 상태 모델은 정합:
- merge_status(draft/review/confirmed): 제출서 단위, 병합 WS
- 클러스터 status(pending/accepted/held/rejected): 클러스터 단위, 비교 WS
- 두 상태축은 **다른 대상**이므로 공존 가능(혼동만 제거하면 됨).

## 3. 감사 결론

### 3.1 심각도 요약
| 문제 | 심각도 | 성격 | 해소 |
|------|--------|------|------|
| 4 동결↔되먹임 | 치명 | 명세서 결함 | 되먹임 별도 테이블(A) |
| 2 확정 용어 | 중대 | 용어 충돌 | 확정/수락 분리 |
| 1 잎 보존 이원화 | 중대 | 저장소 미정의 | 역할 분담(참조=활성, 사본=이력) |
| 5 재매칭↔동결 | 중대 | 4에 종속 | 4 해소 시 자동 |
| 3 draft 제약 | 경미 | 문서 간극 | 명문화 |

### 3.2 핵심 발견
**종합 명세서가 "통합했다"고 선언했으나, 실제로는 5개 정합성 문제가 잠재했다.** 특히 문제 4(동결↔되먹임)는 명세서 자체의 결함으로, "동결"이라는 해법이 시스템에 실재하는 되먹임과 충돌함을 놓쳤다. 이는 개별 설계·검증이 옳아도, **교차 관심사 감사 없이는 통합이 성립하지 않음**을 보여준다.

### 3.3 해소의 수렴점 — 되먹임 분리가 열쇠
5개 중 3개(1·4·5)가 **되먹임 분리**(문제 4의 A)로 함께 해소된다:
- submission_items = 순수 견적 데이터(동결 대상)
- 클러스터 연결(catalog_item_id·match_status·잎 참조) = 별도 매핑 테이블(비교 WS 소유)
- → 동결·되먹임·재매칭·잎 보존이 모두 정합.

이것은 앞서 논의한 "되먹임 서비스 함수 수렴"·"소유권 규칙"의 데이터 모델 실체다. **되먹임 분리를 종합 명세서에 반영하고, 이를 버전 관리(부록 C)의 선결로 승격해야 한다.**

## 4. 명세서 수정 권고 (감사 반영)

종합 명세서에 다음을 반영한다.

1. **§1.2에 되먹임 분리 추가**: 클러스터 연결 필드를 submission_items에서 분리해 별도 매핑 테이블로. 동결↔되먹임 충돌 해소. item_id 동결의 실효성 확보.
2. **용어 표준화 절 신설**: 확정(제출서)/수락(클러스터) 구분. 전 설계서 통일.
3. **잎 보존 저장소 역할 명문화**: 클러스터 멤버(활성·참조) vs 스냅샷(이력·사본).
4. **합계 검증 공통 모듈**: 4종 불변식을 단일 모듈로. ④ 수정을 그 안에서.
5. **다중탭 draft 제약 명문화**: 하위 설계서에도 반영.
