# QDBT — 진화적 아키텍처 로드맵

> 대상 버전: v0.9.8 ~ v0.11.x (점진) · 작성 기준: v0.9.7 코드
> 상태: 설계 확정, 단계별 착수 대기
> **이 문서는 「분리아키텍처 설계서(v1)」의 개정판이다.** v1의 "지금 방식 B로 분리" 전제를 폐기하고, 비판적 검토에서 드러난 결함을 반영해 **"기능 먼저, 분리는 필요가 증명되면"** 원칙으로 재구성한다.

---

## 0. 왜 재설계했는가 — v1의 결함 요약

v1(분리아키텍처 설계서)은 "비교와 병합은 다르다"는 **관찰은 옳았으나**, "지금 방식 B로 분리한다"는 **처방이 성급**했다. 코드 검증으로 드러난 결함:

1. **단방향 의존은 거짓** — v1의 분리 근거였으나, 비교 영역이 병합 소유 테이블(submission_items)을 **8곳에서 쓴다**(compare 3 + clusterer 5). 클러스터 확정 시 catalog_item_id·match_status·category를 되먹임한다. 의존은 **양방향**이다.
2. **done 게이트 부적합** — done은 "추출 완료" 플래그일 뿐 "확정"이 아니다. 환율 수정·특별 네고·분류 이동이 모두 done 이후 일어난다. 상태 모델에 "확정" 개념이 없다.
3. **경계 개념의 소속 불명** — compare_units(비교 개념인데 submissions에 저장), category(병합 데이터인데 비교 화면에서 수정)가 경계를 넘나든다.
4. **방식 B의 효과 불명** — URL/블루프린트만 나누는 것은 실제 문제(bid.html 1943줄 비대화)를 리팩터링으로 해결하는 것과 구분되지 않는다. 결합도는 그대로 남는다.
5. **오버엔지니어링** — 분리 대상 병합 기능(다중탭·트리조립·드래그앤드랍)이 **아직 미구현**. 1인 개발로 조직 분리 이득 없음. 비용만 즉시 발생.
6. **파이프라인 가정 오류** — 워크플로우는 병합→비교 단방향이 아니라 **반복(왕복)**이다.

**결론: 물리적 분리를 목표에서 내리고, 진화적으로 접근한다.**

---

## 1. 설계 원칙 (재정립)

- **관심사 분리는 유지, 물리적 분리는 유보**: 비교와 병합의 개념적 구분은 코드 조직(모듈·파일)에 반영하되, 별도 앱·URL 분리는 필요가 증명될 때까지 하지 않는다.
- **기능이 경계를 드러낸다**: 병합 기능을 실제 구현해야 경계가 어디인지 알 수 있다. 미구현 상태에서 경계를 확정하지 않는다.
- **결합을 부정하지 않고 관리한다**: 양방향 되먹임은 실재한다. 이를 숨기지 말고 **명시적 인터페이스**로 다룬다.
- **각 단계는 독립적 가치**: 다음 단계 없이도 그 자체로 이득. 분리까지 안 가도 손해 없음.
- **되돌릴 수 있게**: 각 단계는 이전으로 회귀 가능. 큰 비가역 결정을 미룬다.

---

## 2. 3단계 로드맵

```
[1단계] 파일·모듈 리팩터링      → 즉각 이득, 낮은 위험, 분리와 무관하게 유효
   bid.html(1943줄) 병합성 편집 UI 분리, compare 라우트 정리
        │
[2단계] 병합 기능 구현          → 실체가 경계를 드러냄
   다중탭 통합 · 트리 조립 · 드래그앤드랍 · 공통 부품 추출
        │
[3단계] (조건부) 워크스페이스 분리  → 선행조건 충족 시에만
   되먹임 인터페이스화 + 확정 상태 도입 후 검토
```

핵심: **1·2단계는 3단계를 전제하지 않는다.** 3단계는 "선행조건"이 충족되고 필요가 증명될 때만 착수한다.

---

## 3. 1단계 — 파일·모듈 리팩터링 (즉시)

### 3.1 목적
분리 없이 즉각적 이득. bid.html 비대화(1943줄, 병합성 편집 요소 21개 폼/핸들러 + 21개 JS 함수)를 해소.

### 3.2 작업
- **템플릿 분해**: bid.html에서 편집 UI를 부분 템플릿으로 추출
  - `_compare_table.html` (순수 비교표 — 읽기)
  - `_cluster_edit.html` (클러스터 이동·수락·병합 — 편집)
  - `_item_move.html` (항목/분류 이동 — 편집)
- **JS 모듈 분리**: 클러스터 편집·드래그·선택 로직을 별도 스크립트로
- **compare 라우트 그룹핑**: 24개 라우트를 주석·순서로 "비교 조회" / "클러스터 편집" 군으로 정리 (파일 이동 없이 논리 구획)

### 3.3 원칙
- **동작 변경 없음**: 순수 리팩터링. URL·기능·DB 불변.
- **회귀 검증**: 분해 전후 렌더·동작 동일 확인.

### 3.4 이득
- 비교 화면 가독성·유지보수성 즉시 개선
- 향후 병합 기능이 붙을 자리 마련
- **분리를 안 해도 이 자체로 완결된 이득**

---

## 4. 2단계 — 병합 기능 구현

### 4.1 목적
설계만 있는 병합 기능을 실체화. 기능이 있어야 경계가 드러난다.

### 4.2 대상 (기존 설계서 참조)
- **다중 탭 통합 추출** (「다중탭추출 설계서」 본문)
- **트리·세부 분리 조립** (동 설계서 부록 A)
- **묶음 펼치기** (「묶음펼치기 설계서」)
- **드래그앤드랍 항목 배치** (트리 노드 ↔ 항목)

### 4.3 공통 부품 추출 (핵심)
병합의 트리 조립과 비교의 묶음 펼치기는 **구조적 동형**. 공통 모듈로 추출해 양쪽이 재사용:

| 공통 부품 | 병합 | 비교 |
|-----------|------|------|
| 노드-잎 귀속 | 세부 항목 → 트리 노드 | 잎 → 클러스터 |
| 합계 검증기 | Σ배치 == 노드 소계 | Σ잎 == 묶음 |
| 드래그앤드랍 UI | 항목 → 노드 | 잎 → 클러스터 |
| 이름 매칭(편차 흡수) | 탭명 ↔ 노드명 | 잎경로 ↔ compare_units |

→ 이 부품들이 **자연스러운 공유 레이어**가 된다. 인위적 분리가 아니라 실제 재사용에서 도출.

### 4.4 이득
- 실제 병합 기능 확보 (사용자 핵심 요구)
- 공통 부품이 어디에 필요한지 실증 → 3단계 경계의 근거
- **분리를 안 해도 병합 기능은 완결**

---

## 5. 3단계 — (조건부) 워크스페이스 분리

### 5.1 착수 선행조건 (모두 충족 시에만)
아래가 충족되지 않으면 **분리하지 않는다.** v1의 실패를 반복하지 않기 위한 게이트.

1. **되먹임 인터페이스화 완료**: 비교→병합 쓰기 8곳을 명시적 서비스 함수로 통일. 직접 UPDATE 제거, "비교가 병합에 요청하는" 단일 창구 확립.
2. **확정 상태 도입**: done(추출 완료)과 별도로 "병합 확정" 상태 추가. 확정 = 비교 준비 완료. 상태 전이 명확화.
3. **경계 개념 정리**: compare_units·category의 소속과 편집 권한 확정.
4. **분리 필요 증명**: 다인 개발·독립 배포 등 실제 필요 발생. 1인·단일 배포면 불필요.

### 5.2 분리 방식 (선행조건 충족 시)
- 선행조건이 되면, v1의 방식 B(논리 분리)를 **되먹임 인터페이스 위에서** 재설계
- 이때 경계는 done이 아니라 "확정 상태"
- 블루프린트 경계가 미래 방식 A(완전 별도 앱) 승격 대비

### 5.3 되돌림
- 선행조건 미충족·필요 미증명 시 3단계는 **영구 보류 가능**
- 1·2단계 이득은 그대로 유지

---

## 6. 결합 관리 — 되먹임을 숨기지 않는다

v1이 부정했던 양방향 되먹임을 정면으로 다룬다. 현재 비교→병합 쓰기 8곳:

| 위치 | 쓰기 대상 | 성격 |
|------|-----------|------|
| compare.py ×3 | submission_items.category | 분류 이동 |
| clusterer.py ×5 | submission_items.catalog_item_id·match_status·category | 클러스터 확정 되먹임 |

**관리 방침** (1단계부터 점진):
- 이 8곳을 **명시적 서비스 함수**로 수렴 (예: `apply_cluster_result_to_items()`)
- 비교가 병합 데이터를 "직접 UPDATE"하지 않고 "서비스 호출"로
- 이 인터페이스가 3단계 분리의 토대 (선행조건 1)

---

## 7. 상태 모델 재설계 (3단계 선행)

현재: `extraction_status` = pending / processing / done / failed (단일 축)

문제: done이 "추출 완료"와 "비교 준비"를 겸함.

**제안** (3단계 착수 시): 상태 축 분리
- `extraction_status`: pending → processing → done (추출 파이프라인)
- `merge_status`(신규): draft → confirmed (병합 확정 여부)
- 비교 WS는 `merge_status='confirmed'`만 참조 → 진짜 게이트

단, 이는 3단계 선행조건이므로 **1·2단계에서는 도입하지 않는다**(미충족 시 불필요한 스키마 변경 회피).

---

## 8. 단계별 이득·비용·위험

| 단계 | 이득 | 비용 | 위험 | 착수 조건 |
|------|------|------|------|-----------|
| 1 리팩터링 | 즉시 가독성·유지보수 | 낮음(수 파일) | 낮음(동작 불변) | 즉시 |
| 2 병합 기능 | 핵심 기능 확보 | 중(기능 구현) | 중(신규 로직) | 1단계 후 |
| 3 분리 | 관심사 물리 분리 | 높음(재편성) | 높음(결합 정리) | 선행조건 4개 충족 시 |

**핵심**: 위험·비용이 단계마다 커지고, 착수 조건이 엄격해진다. 낮은 위험부터, 필요가 증명된 만큼만.

# 부록 B — 리뷰·확정 프로세스 (아키텍처 중심 골격)

> 본문의 3단계 로드맵을 **재편하는 핵심 보강**. 병합과 비교 사이에 명시적 "리뷰·확정" 프로세스를 두어, done 게이트 부적합(결함 2)·되먹임(결함 1)·반복 워크플로우(결함 6)를 한꺼번에 규율한다.
> 확정 결정: 4단계 리뷰 루프 · 확정본 버전 관리 · 제출서별(업체 단위) 확정

## B.1 왜 중심 골격인가 — 흩어진 검증의 통합 게이트

현재 검증이 파편화되어 있다(코드 확인됨): 도메인 분류 정합은 추출 직후, 합계 정합은 추출 시 계산만, 환율 확인은 상세 패널, 노드 소계·묶음 불변식은 각 기능에 흩어질 예정. **하나로 모으는 관문이 없다.**

리뷰·확정 프로세스가 이 검증들을 **단일 게이트로 수렴**시킨다. "확정 = 모든 검증 통과"라는 단일 의미를 부여해, 단계는 세분화되나 절차는 명료해진다.

## B.2 아키텍처 재편 — 2 워크스페이스 → 3 프로세스

```
[병합·구성]          [리뷰·확정·검증]              [비교·분석]
견적서 조립    ──▶   통합 검증 + 확정 + 버전   ──▶   확정본 비교·축적
 (draft)            (review 루프 → confirmed)        (confirmed만 참조)
```

- 리뷰·확정이 병합의 **출구**이자 비교의 **입구** = 명확한 핸드오프
- 비교 WS는 `confirmed`만 참조 → done보다 견고한 진짜 게이트(결함 2 해결)

## B.3 4단계 리뷰 루프 (확정 관문 동작)

확정 결정: **시스템 제안 → 사람 수정 → 시스템 리뷰 → 사람 확정**

```
① 시스템 제안   : 자동 통합 검증 실행 → 통과/실패 항목 제시
                  (합계 불변식·노드 소계·도메인 분류·통화 환율)
② 사람 수정     : 실패 항목만 교정 (분류 이동·환율 입력·배치 보정)
③ 시스템 리뷰   : 재검증 → 잔여 실패 표시 (①로 순환 가능)
④ 사람 확정     : 모든 검증 통과 시 확정 → confirmed + 버전 부여
```

- 시스템이 검증을 자동 수행하므로 **1인 운영에서도 형식적 병목이 아님**(사람은 실패만 판단)
- 모두 통과 시 ④는 거의 자동에 가까움

## B.4 확정본 버전 관리 (핵심)

확정 결정: 확정 후 수정 시 **트리구조·분류 유지 원칙**, 세부 항목(품목·단가)은 수정 가능, **수정본으로 버전을 올려 관리.**

### 원칙
- **구조 안정성**: 트리(계층)·분류는 확정 후 유지 → 비교·클러스터링의 기준 불변
- **내용 가변성**: 세부 항목(품목·단가·수량·금액·환율)은 수정 가능
- **버전 승격**: 확정본 수정 시 새 버전으로 확정 (v1 → v2)

### 상태·버전 모델 (신규)
```
merge_status: draft → review → confirmed
confirm_version: 1, 2, 3, ...  (confirmed 시 부여·증가)
confirmed_at: 확정 시각
```
- draft: 편집 중 (자유 수정)
- review: 4단계 루프 진행 중
- confirmed(vN): 확정본. 비교 WS가 참조

### 버전과 되먹임·이력 정합 (결함 1·가격이력 해결)
- **비교 WS는 최신 confirmed 버전을 참조.** 클러스터·가격이력이 어느 버전 기준인지 명확.
- 확정본 수정 → v2 확정 시: v1 기반 클러스터·이력은 "v1 기준"으로 보존, v2는 재검토 유도.
- price_history의 기존 `spec_snapshot`(당시 스냅샷) 방식을 버전에 확장 — 이력이 버전 시점을 기록.
- 되먹임(비교→병합 쓰기 8곳)은 confirmed 버전에만 적용, draft는 병합 WS 전용 → 결합이 버전 경계로 규율됨.

## B.5 재확정 정책 (차등 재검증)

확정 후 수정 시 변경 범위에 따라 재검증 범위를 달리한다(전체 재리뷰 강제 회피).

| 변경 | 트리·분류 | 재검증 범위 | 버전 |
|------|-----------|-------------|------|
| 환율 수정 | 유지 | 합계 정합만 | +1 |
| 단가·수량 수정 | 유지 | 합계·소계 정합 | +1 |
| 품목 추가/삭제 | 유지(가능하면) | 합계·노드 소계 | +1 |
| 트리·분류 변경 | 변경 | 전체 재검증 | +1 (구조 변경 표시) |

- 트리·분류 유지가 원칙이므로 대부분 부분 재검증으로 충분
- 구조 변경은 예외적이며 전체 재검증 + 비교 재클러스터링 유도

## B.6 확정 단위 — 제출서별(업체 단위)

확정 결정: **제출서별 확정.** 각 업체 견적서를 독립적으로 확정.

- 한 업체 견적이 준비되면 즉시 확정 가능 (다른 업체 대기 불필요)
- 비교는 confirmed 제출서들이 모이면 수행
- 입찰 내 일부만 확정된 상태도 자연스럽게 표현(부분 비교 가능)

## B.7 로드맵 반영 — 리뷰·확정을 어느 단계에

| 로드맵 단계 | 리뷰·확정 관련 |
|-------------|----------------|
| 1 리팩터링 | 변화 없음 (검증 로직은 현 위치 유지) |
| 2 병합 기능 | 병합 기능 구현과 함께 **통합 검증 게이트 신설**, merge_status·버전 도입 |
| 3 (조건부) 분리 | 리뷰·확정이 이미 병합/비교 경계를 명확히 하므로, **분리 필요성 자체가 낮아짐** |

**중요**: 리뷰·확정 프로세스는 **3단계(물리 분리) 없이도** 병합/비교 경계를 명료하게 만든다. 즉 이 프로세스가 도입되면 결함 2·6이 해소되어, 물리적 분리의 실익이 더욱 줄어든다. **리뷰·확정이 분리의 대안이 될 수 있다.**

## B.8 비판적 검토 (이 프로세스의 잔여 위험)

- **버전 폭증**: 사소한 수정마다 버전이 오르면 관리 부담. → 버전은 confirmed 재확정 시에만(draft 편집은 버전 무관). 필요 시 버전 정리(prune) 정책.
- **비교가 참조하는 버전의 모호성**: 여러 업체가 서로 다른 버전이면? → 비교는 각 제출서의 "최신 confirmed"를 참조, 버전 표기로 투명화.
- **구조 유지 원칙의 경직성**: 트리·분류를 정말 못 바꾸나? → 원칙은 유지지만, 구조 변경은 "전체 재검증 + 구조변경 표시"로 예외 허용(B.5).
- **리뷰 루프 무한 순환**: ①③ 순환이 끝나지 않으면? → 잔여 실패를 "확정 보류 사유"로 명시, 사용자가 예외 승인(override)으로 강제 확정 가능(사유 기록).

## B.9 미결 사항 (다음 리뷰)

- 버전 저장 방식: 전체 스냅샷 vs 델타(변경분만). 저장 비용 vs 복원 편의.
- 예외 승인(override) 확정의 권한·기록 범위
- 비교 재클러스터링 유도의 자동/수동 (v2 확정 시 기존 클러스터 처리)
- merge_status·confirm_version 스키마의 도입 시점 (2단계 어느 시점)
- 확정 취소(재편집 위한 draft 복귀)의 절차와 비교 영향

# 부록 C — 확정 스냅샷·취소 (버전 관리 구체화)

> 부록 B의 버전 관리를 구체화. 확정 결정: **스냅샷 저장(+ 스냅샷 단독 다운로드)** · **확정 취소 가능(휴먼 오류 대비).**
> 이 둘이 결합하면 버전 관리 시스템의 커밋·되돌리기 모델이 된다: 확정=커밋(불변 스냅샷), 취소=되돌리기(작업본 복귀, 스냅샷 보존), 재확정=새 커밋.

## C.1 스냅샷 저장 (전체 상태, 불변)

### 결정
델타가 아닌 **전체 스냅샷**. 확정 시점 제출서의 완전한 상태를 하나의 불변 기록으로 저장.

### 근거 (일관성)
기존 `price_history`가 이미 스냅샷 방식(item_path·spec_snapshot으로 당시 상태 보존). 확정 스냅샷도 동일 철학 → 시스템 전체가 "시점 스냅샷"으로 일관.

### 스키마 (신규)
```
submission_snapshots
  snapshot_id      PK
  submission_id    FK
  version          INTEGER          -- 1, 2, 3...
  snapshot_json    TEXT             -- 확정 시점 전체 상태(항목 트리·통화·환율·소계·nego)
  subtotal         REAL             -- 확정 소계(빠른 조회용)
  fx_snapshot      TEXT             -- 확정 환율 맵
  status           TEXT             -- active | superseded | cancelled
  confirmed_at     TIMESTAMP
  confirmed_by     TEXT
```
- `snapshot_json`: submission_items 전체 트리 + 메타. 확정 순간의 완전 복원 가능.
- `status`: active(현재 유효) / superseded(다음 버전에 밀림) / cancelled(취소됨). **스냅샷은 삭제하지 않음**(감사 추적).

### 스냅샷 단독 다운로드
- 확정본을 독립 파일로 export (감사·백업·외부 공유용)
- 형식: 원본 구조 재현 Excel(기존 `excel_report` 재사용) + 원시 JSON 선택
- 어느 버전이든 다운로드 가능(과거 확정본 포함) → 이력 추적성

## C.2 확정 취소 (되돌리기)

### 결정
확정은 **취소 가능**. 휴먼 오류(실수 확정·잘못된 확정)에 대한 복원력.

### 상태 전이 (확장)
```
draft ──confirm──▶ confirmed(vN) ──cancel──▶ draft
  ▲                                            │
  └────────────── 재편집 ───────────────────────┘
재확정 시 v(N+1) 생성 (버전은 되돌아가지 않고 증가)
```

### 취소 처리 규칙
- `merge_status`: confirmed → draft
- 활성 스냅샷: status = **cancelled** (삭제 아님, 보존)
- 버전 번호: **되돌리지 않음.** 취소 후 재확정 시 다음 번호(vN 취소 → 재확정은 v(N+1)).
  이유: 버전은 "확정 시도의 이력"이므로 단조 증가. 감사 추적 일관성.
- **비교 영향 처리**(핵심): 취소된 제출서를 참조하던 클러스터·비교·이력은 **무효 신호**.
  → 해당 입찰의 비교 재검토 유도(자동 재클러스터링 아님, 사용자 확인).

### 안전장치 (남용 방지)
- 취소는 명시적 확인 + 사유 기록
- 비교 영향 경고: "이 확정본으로 만든 비교/클러스터가 무효화됩니다" 명시
- confirmed_by ≠ 취소자인 경우 권한 확인(선택)

## C.3 커밋·되돌리기 모델로서의 정합성

| VCS 개념 | QDBT 대응 | 불변성 |
|----------|-----------|--------|
| 커밋 | 확정 (스냅샷 생성) | 스냅샷 불변 |
| 되돌리기 | 확정 취소 (draft 복귀) | 취소 스냅샷 보존(cancelled) |
| 새 커밋 | 재확정 (다음 버전) | 새 스냅샷 |
| 이력 | 버전별 스냅샷 목록 | 전량 보존 |

- **작업본(draft)과 확정본(snapshot) 분리**: draft 편집은 스냅샷에 영향 없음. 확정 시에만 스냅샷 생성.
- **되돌림 가능·이력 불변**: 상태는 오가되(draft↔confirmed), 스냅샷 이력은 단조 누적.

## C.4 비판적 검토 (잔여 위험)

- **취소 남용 → 상태 불안정**: 잦은 확정/취소로 비교가 계속 무효화. → 취소 사유 기록·빈도 가시화. 취소는 예외적 행위로 설계(기본 흐름은 재확정 by 버전 승격).
- **스냅샷 저장 용량**: 전체 스냅샷 누적 → 용량 증가. → submission 단위라 규모 제한적(항목 수십~수백). 필요 시 오래된 superseded 스냅샷 압축·아카이브.
- **취소 시점 비교 데이터의 처리**: 이미 쌓인 price_history는? → 취소는 이력을 삭제하지 않고 "cancelled 버전 기반"으로 표시. 이력의 감사 가치 보존.
- **다운로드한 스냅샷의 신뢰**: 외부 공유된 스냅샷이 최신이 아닐 수 있음. → 스냅샷에 버전·확정시각·status 명기(워터마크).

## C.5 미결 사항 (다음 리뷰)

- snapshot_json 구조 상세(항목 트리 직렬화 포맷)
- 취소 후 비교 재검토: 자동 무효 표시 vs 수동 재클러스터링 트리거 범위
- superseded 스냅샷 보관 기간·아카이브 정책
- 스냅샷 다운로드 형식 확정(Excel 재현 vs JSON vs 양쪽)
- 확정 취소 권한 모델(확정자 본인 vs manager 이상)
