# QDBT 스티칭 자체 3단계 항목 연결 — 구현 계획 (2026-07-11, 계획 전용)

> **방향 정정**: 스티칭은 **자체적으로** 항목 연결 3단계 원칙을 갖는다 —
> **① 완전합치(코드) → ② LLM 유사 합치 '제안' → ③ 사람 확정**.
> 이전 문서의 "스티칭=무LLM 결정론, 유사는 다운스트림 클러스터링에 위임"은 **폐기**한다.
> 대상 축: **한 제출서 내 시트 간(intra-submission cross-sheet) 항목 연결**
> (cross-vendor 카탈로그 클러스터링과 축이 다름).
>
> 본 문서는 **계획만** 담는다(구현은 확인 후). 비파괴·정본(`submission_items`) 불변·총액 Δ=0 준수.

---

## 0. 현재 상태 / 근거

- ① 완전합치(코드)는 이미 있음: `stitch._dedup_and_rollup` (A) 완전중복 dedup(정규화 경로+품명+
  규격+금액 정확일치) + (B) 요약행 roll-up.
- 직전에 넣었던 코드-종결 `cross_sheet_similar` 플래그는 **② LLM 단계를 건너뛴 오종결**이라 제거함.
  → 지금은 유사 항목이 '별도 잎으로 보존'만 되고 **연결 제안이 생성되지 않는 공백** 상태.
- 재사용 자산:
  - `extractors.catalog_clusterer.run_clustering(items, api_key, …)` — LLM 유사도 클러스터
    (반환: `{representative_item_id, duplicate_item_ids, similarity_score, similarity_summary}`),
    `EXACT_MATCH_PREPASS`로 0단계 코드 완전일치 프리패스, 청크 처리 내장.
  - `extractors.matcher.run_llm_matching` — item↔catalog LLM 매칭(`match_status='suggested'`).
  - `web/blueprints/submissions.py`
    - `residuals/suggest`(라우트): residual에 LLM/휴리스틱 **상위 분류 경로** 제안(항목↔경로).
    - `_build_residual_view` / `map_config.stitch.{residuals,candidates}` 저장·표시.
    - `/link`(연계 캔버스), `/link/node`(exclude·residual·delete), `/link/confirm`(스냅샷 동결).
    - `link_overrides`(수기 미연계 표시), `get_user_llm_settings`+`get_provider`(LLM 접근).

## (a) LLM 유사 단계를 어디에 넣을지

**결론: 추출(headless) 인라인 금지 → 온디맨드 제안 라우트.**

- 스티칭 추출은 **헤드리스**(업로드 추출·크론·테스트)로 돌고 **LLM 키/컨텍스트가 없을 수 있다**.
  따라서 `_run_stitch()` **안에서 LLM을 직접 호출하지 않는다**(폐쇄망·무키에서 추출이 깨지면 안 됨).
- 대신 **기존 `residuals/suggest` 패턴과 동일하게**, 추출은 **① 코드 완전합치 + '유사 후보(link_candidates)'
  산출**까지만 하고, **② LLM 유사 제안은 별도 온디맨드 라우트** `POST /<sid>/links/suggest`가 담당.
  - "스티칭이 자체 3단계를 갖는다" = **스티칭 기능/플로우가 3단계를 소유**한다는 뜻이며,
    ②는 이 플로우에 속하되 사용자가 LLM을 구성한 시점에 온디맨드로 호출된다(추출과 분리).
- 코드 stage-1의 후보 산출 지점: `_run_stitch` 말미(정본 잎 확정 후)에 `_detect_link_candidates(items)`
  추가 → `stitch_info["link_candidates"]`로 `map_config.stitch`에 저장(비파괴).

## (b) 기존 clusterer/matcher LLM 유사도 재사용 / 분리

**재사용 최대화 + 입력 스코프·프롬프트 프레이밍만 분리.**

- **재사용**: `run_clustering(items, api_key, …)`의 LLM 유사도 엔진·청크·프로바이더 스캐폴딩을 그대로 사용.
- **분리(축 차이 반영)**: 새 얇은 어댑터 `extractors.stitch_link.suggest_cross_sheet_links(submission_id or items, llm)`:
  1. **입력 스코프**: 전체 bid가 아니라 **이 제출서의 `link_candidates` 항목만**(시트 간 후보) 투입.
  2. **프레이밍**: 프롬프트 힌트를 "한 견적서의 **서로 다른 시트**에 중복 기재된 **동일 라인아이템**인가?"
     로(카탈로그 '동종 품목'보다 엄격한 '동일 항목' 임계). 각 후보에 `_sheet` 태그를 실어
     **제안은 반드시 서로 다른 시트의 항목쌍**만 연결.
  3. **출력 정규화**: `{group:[item_ids], representative_item_id, score, summary, method:'llm'|'heuristic'}`.
- 두 엔진(clusterer=cross-vendor, stitch_link=intra-submission)은 **입력·프레이밍만 다르고 코어 공유**.

## (c) 제안 저장 위치(비파괴, 정본 불변) 및 표시

- **저장(전부 `map_config`, `submission_items` 불변)**:
  - `map_config.stitch.link_candidates` — ① 코드 후보(group·key·sheets).
  - `map_config.stitch.link_suggestions` — ② 제안(group·representative·score·summary·method·status:'proposed').
  - `map_config.link_confirmations` — ③ 사람 확정(group_id→{status:accepted|rejected, representative, by, at}).
- **표시**:
  - **residual 패널**: 기존 residual 목록에 "유사 연결 제안" 카드 추가(항목↔항목, 신뢰도·요약 표시).
    `residual reason='cross_sheet_link_suggested'`(비종결: 제안 대기/확인 대기 의미).
  - **연계 캔버스(/link)**: 제안된 두 잎을 점선(제안)으로 잇고, accept 시 실선(확정)으로.

## (d) 사람 확정 UI 연결

- 신규 라우트 `POST /<sid>/links/confirm` (또는 `/link/node`에 `action∈{link,unlink}` 추가):
  - `accept`: `link_confirmations[group]='accepted'` + 대표 지정. **기본 링크만(구조/표시)** → 총액 Δ=0.
  - `reject`: `'rejected'` 기록 → 제안 목록에서 내려감(후보는 별도 잎 유지).
  - (선택·명시적) `accept_and_dedup`: 사람이 '동일 항목 이중계상'으로 확정하면 중복 잎을
    `set_item_excluded(is_header=1)`로 **명시적** 제외(되돌리기 가능). 이때만 총액 변함 —
    **자동 아님, 사람의 별도 결정**.
- 미확정 제안·후보는 **'미연계=LLM 제안 실패 또는 사람 확인 대기'** 상태로만 남는다(종결 아님).

## (e) LLM 없음/폐쇄망 등 원칙 못 지킬 지점과 처리

- **추출 헤드리스**: ②를 인라인하지 않음으로 해결(위 (a)). 추출은 무키에서도 정상.
- **무키/폐쇄망에서 ② 호출 시**: `run_clustering` 대신 **결정적 휴리스틱 유사도**(정규화 품명 토큰
  겹침·규격·금액 근접, `_heuristic_pick` 계열)로 **제안 생성**, `method='heuristic'` 명시.
- **휴리스틱도 확신 없음**: 후보를 **'pending 사람 확인'**으로 남김(자동 병합·종결 금지).
  → ② 단계를 '시도'는 하되 실패 시 skip이 아니라 **사람에게 넘김**(원칙 유지).
- **하드 블록 없음**: 3단계는 온디맨드 ②로 충족 가능. 단, 아래는 **결정 필요**.

## 단계별 구현(예정, 작은 커밋)

1. `stitch._detect_link_candidates` + `stitch_info.link_candidates`(코드 후보, 비파괴). 견고성 테스트.
2. `extractors/stitch_link.py`: `suggest_cross_sheet_links`(run_clustering 재사용 + intra-submission 어댑터
   + 휴리스틱 폴백). 함수 직접 호출 테스트(LLM 목/스텁).
3. 라우트 `links/suggest`·`links/confirm`(또는 `/link/node` 확장) + `map_config` 저장.
4. residual 패널/연계 캔버스 표시(제안 카드·점선). jsdom/스냅샷 검증.
5. 견고성 매트릭스에 '유사 연결 제안(코드후보→LLM/휴리스틱 제안→사람 확정)' 시나리오 추가, 실샘플 Δ=0.
6. CHANGELOG·본 계획 문서 갱신(구현 완료 반영).

## 불변식 / 회귀 게이트

- **정본 불변**: `submission_items` 미변경. 후보·제안·확정은 전부 `map_config`.
- **총액 Δ=0**: 링크는 구조/표시. `recompute_subtotal` 무영향. 총액 변화는 사람의 명시적
  `accept_and_dedup`(제외) 시에만, 되돌리기 가능하게.
- **실샘플 15개/31시트 stitch 총액 Δ=0** 회귀 유지(후보 산출은 비파괴이므로 자동 충족, 테스트로 확인).

## 결정 필요 (착수 전/중 확인)

1. **② 어댑터 방식**: `run_clustering` 재사용(입력 스코프+프롬프트 힌트) vs intra-submission 전용
   프롬프트 신설. → 권장: **재사용+어댑터**. 단, '동일 라인아이템' 의미가 '동종 품목'과 크게
   벗어나면 전용 프롬프트 필요 — **구현 중 검증**해 필요 시 보고.
2. **후보 탐지 기준(stage-1 코드)**: 어느 유사도까지 후보로 올릴지(정규화 품명 완전일치·다른 경로만?
   토큰 겹침 임계?). 넓으면 제안 과다, 좁으면 누락. → 초기값 **'정규화 품명 동일 + 다른 분류경로(시트
   경계) + 금액 근접'**으로 보수적 시작, 튜닝은 후속.
3. **accept 기본 동작**: 링크만(Δ=0) vs 이중계상 제외까지. → 권장 **링크만 기본**, 제외는 별도 명시 액션.
4. **표시 위치 우선순위**: residual 패널 먼저 vs 연계 캔버스 먼저. → 권장 **residual 패널 먼저**(기존
   제안 UI 재사용 최소변경), 캔버스 점선은 후속.
