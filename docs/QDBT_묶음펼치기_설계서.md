# QDBT — 묶음 펼치기(다층 비교) 설계서

> 대상 버전: v0.9.8 (예정) · 작성 기준: v0.9.7 코드
> 상태: 설계 확정, 구현 착수 전
> 핵심 개념: 단순 UI 펼침이 아니라, 서로 다른 계층 구조로 제출된 견적을 **어느 레벨에서든 정합 비교**하는 다층 비교(multi-level comparison) 기능

---

## 1. 요건 정의

### 1.1 배경 — 왜 필요한가

업체마다 견적서의 계층 구조(트리 깊이)가 다르다. **한 업체의 소분류가 다른 업체의 품목(잎) 레벨과 같은 층위**인 경우가 실재한다.

- **E시스템즈(H 케이스)**: `자재 > 서버 장비 > [랙형 서버, GPU 가속 서버, 관리 서버]` — "서버 장비"는 소분류, 그 아래가 잎
- **D·A**: `자재 > GPU Server` — "GPU Server"가 곧 품목(잎) 레벨

같은 물건(GPU 서버)이 업체마다 다른 트리 깊이에 놓인다. 분류 레벨로 비교하면 E의 "서버 장비"(3개 합계)와 D·A의 개별 품목이 레벨이 어긋나 직접 비교되지 않는다. **펼치기는 이 깊이 차이를 흡수해 동일 물건을 같은 레벨에서 만나게 하는 장치**다.

### 1.2 3대 불변 요건 (설계 제약)

1. **합계 보존 (invariant)**: 묶음을 잎으로 펼쳤을 때 `Σ(잎 금액) == 묶음 금액`. 펼침은 "같은 돈을 더 잘게 보여주는 것"이며 값을 바꾸지 않는다. 기존 원칙(공급가액 = 트리 = 라인 합계)의 연장.
2. **레벨 어긋남 흡수**: 업체마다 다른 트리 깊이를 흡수해, 동일 물건이 트리 깊이와 무관하게 같은 레벨에서 매칭된다.
3. **소/중분류 클러스터링 유지**: 분류 레벨 비교는 기존 요건으로 유지된다. 펼침은 이를 대체하지 않고, 그 위에 **선택적으로 잎까지 내려가는 층**을 얹는다.

### 1.3 확정된 설계 결정

| 항목 | 결정 |
|------|------|
| 펼침 깊이 | 통상 트리처럼 **잎 단위까지 선택적** 펼침 (임의 깊이 재귀) |
| 펼친 잎의 의미 | **비교·매칭 대상** (가격 이력도 잎 단위로 적재) |
| 잎 보존 시점 | **묶음 확정 시 잎까지 함께** 클러스터에 보존 (스냅샷 고정) |
| 합계 관계 | **묶음 가격 = 잎 합계** (저장·조회 양쪽에서 자동 검증) |
| 매칭 전략 | **전략 A — 2단계 계층**(묶음 매칭 → 펼침 시 잎 재매칭) |
| 잎 매칭 보정 | **자동 재매칭 후 수동 조정** 허용 |

## 2. 매칭 전략 — 2단계 계층 클러스터링 (전략 A)

### 2.1 동작 모델

```
[1단계] 묶음 레벨 클러스터링 (기존 유지)
   E "서버 장비" ↔ D·A 상위  — 분류 레벨 비교
        │
        ▼  사용자가 특정 클러스터를 "펼침"
[2단계] 잎 레벨 재클러스터링 (국소, 펼친 클러스터 범위 내)
   E [랙형 서버, GPU 가속 서버, 관리 서버]
   D·A [Rack Server, GPU Server, Management Node]
        → 잎끼리 재매칭 → GPU 가속 서버 ↔ GPU Server
        │
        ▼  자동 재매칭 결과가 틀리면
[보정] 사용자가 잎을 수동 재배치
```

### 2.2 전략 A 선택 근거

3대 요건을 모두 만족하는 유일한 현실적 방식이다.

- **분류 레벨 클러스터링 그대로 유지** → 요건 3 충족
- **펼침 시 국소적으로 잎 재매칭** → 요건 2(레벨 흡수) 충족, 오매칭 위험이 펼친 범위로 국소화
- **잎 합계가 묶음과 일치하도록 검증** → 요건 1(합계 보존) 충족

대안 비교:
- **전략 B(항상 잎 매칭)**: 매칭은 정확하나 "소/중분류 클러스터링 유지"(요건 3)와 충돌 → 제외
- **전략 C(이중 트랙)**: 완전하나 두 클러스터 결과가 모순될 때 정합 로직이 복잡, 실사용 혼란 위험 → 보류

### 2.3 전략 A의 약점과 보완

**약점**: 묶음 매칭이 틀리면(E "서버 장비"가 D·A의 올바른 상위와 안 묶이면) 잎 재매칭도 그 안에 갇힌다.

**보완**:
1. **수동 보정** (확정): 자동 재매칭 후 사용자가 잎을 클러스터 간 재배치. 기존 "미분류만 재검토"·배지 이동 UX 패턴 재사용.
2. **재사용 인프라**: `run_clustering`이 임의 항목 집합에 국소 클러스터링을 수행하므로 잎 재매칭에 그대로 응용. `_unmatched_worker`가 부분 재클러스터링 작업 패턴을 이미 제공.

## 3. 계층별 영향도

### 3.1 데이터 모델 — 잎 보존(role 확장)

**현재 상태**: 묶음일 때 클러스터에 저장되는 것은 묶음의 첫 잎 `item_id` 하나(`first_item_id`)뿐. 하위 잎은 `members`에 **품목명 문자열로만** 참조(실제 item_id·금액 없음). → 펼쳐 보여줄 잎 데이터 자체가 클러스터 결과에 없음.

**변경 방향**: `catalog_cluster_members.role` 컬럼 활용.
- 현재 role 사용값: `'representative'`, `'duplicate'`
- 추가: `'leaf'` (묶음 하위 잎) — 스키마 변경 없이 컬럼 재활용 가능
- 잎 보존 시 각 잎의 실제 `item_id`·`amount`를 함께 저장 (합계 검증용)

**영향 파일**: `catalog_clusterer.py`(save_clusters), `queries.py`(list_submission_items_for_clustering, compare_bid_submissions)

### 3.2 카탈로그 — 매칭·이력 입도 변화

`catalog_cluster_members.catalog_item_id = submission_items.item_id` 관계로 인해, 잎을 클러스터에 편입하면 잎도 카탈로그 매칭·가격 이력 대상이 된다.

- **지금**: 묶음 대표 하나만 카탈로그 매칭 → 이력이 묶음 단위
- **변경 후**: 각 잎이 개별 카탈로그 품목과 매칭 → **가격 이력이 잎 단위로 적재** (요건: 잎도 비교·매칭 대상)
- **영향**: `price_history` 적재 단위, `catalog_suggestions`(잎별 제안), 카탈로그 원장 정합

### 3.3 기준정보 — 임의 깊이 트리 대응

펼침의 정의가 "비교 단위 아래 잎"인데, 잎의 분류·경로는 도메인별 기준정보 체계를 따른다. 도메인마다 트리 깊이·분류 구성이 다르므로(설비·용역은 IT와 계층 상이), **펼침은 특정 깊이를 가정하지 않고 임의 깊이 트리를 재귀 처리**해야 한다. (전 도메인 확장 원칙)

### 3.4 표시·상호작용 — bid.html

기존 3계층(트리 통일 표시·통화 2단·분류/금액 정렬)과 상호작용한다.

- 펼친 잎 행의 통화 표시 규칙 (2단 표시 재적용)
- 펼침 상태에서 금액 정렬이 잎까지 내려가는지
- 트리 경로 통일 필터(treepath_above)의 잎 적용
- **업체별 잎 구성·개수 상이**(E는 3개, D는 개별) → 펼친 행의 업체 열 정렬 로직
- 접힘/펼침 상태 관리, 수동 재배치 UI

## 4. 구현 단계 (제안)

각 단계 종료 시 배포·검증·협의 후 다음으로 진행 (그룹 단위 배포 원칙).

**1단계 — 데이터 기반**: 묶음 확정 시 잎 보존(role='leaf', item_id·amount 저장) + 합계 검증(`Σ잎 == 묶음`). 스키마 영향 최소(role 재활용). 이 단계는 화면 변화 없이 데이터만 확보.

**2단계 — 조회·표시**: `compare_bid_submissions`가 보존된 잎을 반환하도록 확장. bid.html에 펼침/접힘 토글 + 잎 행 렌더(통화·정렬·트리 통일 재적용). 표시 전용, 아직 잎 매칭 없음.

**3단계 — 잎 재매칭(자동)**: 펼침 시 국소 `run_clustering`으로 잎끼리 재매칭. `_unmatched_worker` 패턴 재사용. E의 잎 ↔ D·A 잎 자동 연결.

**4단계 — 수동 보정**: 잎 클러스터 간 재배치 UI(배지 이동·드래그 패턴 재사용). 자동 결과 교정.

**5단계 — 카탈로그·이력 정합**: 잎 단위 카탈로그 매칭·가격 이력 적재. price_history 입도 전환.

---

## 5. 검증 기준

- **합계 불변식**: 모든 펼침에서 `Σ(잎 금액) == 묶음 금액` (자동 검증·경고)
- **레벨 정합**: E의 "GPU 가속 서버" 잎이 D·A의 "GPU Server"와 같은 잎 클러스터에 매칭
- **회귀 없음**: 얕은 트리(D·A) 기존 비교 동작 불변, 분류 레벨 클러스터링 유지
- **도메인 무관**: 임의 깊이 트리에서 펼침 정상 동작 (IT·설비·용역)
- **스냅샷 고정**: 확정 후 원본 변경이 확정 당시 잎 구성과 어긋나지 않음

## 6. 리스크와 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 묶음 매칭 오류가 잎 매칭을 가둠 | 잎 재매칭 실패 | 수동 보정(4단계) |
| 잎 단위 이력 전환 시 기존 이력과 입도 불일치 | 이력 분석 혼선 | 전환 시점 명시, 묶음/잎 이력 병행 기록 검토 |
| 업체별 잎 개수 상이로 행 정렬 붕괴 | 표시 왜곡 | 잎 매칭 클러스터 기준으로 행 구성(빈 셀 허용) |
| LLM 잎 재매칭 비용·지연 | UX 저하 | 국소 범위 한정, 펼침 시에만 수행, 결과 캐시 |
| 합계 불일치(데이터 오류) | 비교 신뢰성 | 저장·조회 양쪽 검증, 불일치 시 경고·차단 |

## 7. 미결 사항 (구현 착수 전 확인)

- 잎 단위 가격 이력 전환 시, 기존 묶음 단위 이력과의 병행/전환 정책
- 수동 보정 UI의 구체 상호작용(드래그 vs 배지 이동 vs 체크박스 이동)
- 펼침 상태의 지속성(세션 유지 vs 매번 접힘)
- 2차 잎 클러스터링 결과의 저장 여부(캐시 vs 매번 재계산)
