## HIGH

### H1. `_to_number`가 ¥·€·元 통화기호·괄호음수·유럽식 소수점을 처리 못 함 (extract 파이프라인)
- **[extract_by_mapping.py:57-64]**
- 심각도: **HIGH**
- 문제: `s.replace(",","").replace(" ","")` 후 `for sym in ("₩","원","$","USD","\\")` 만 제거. `_CUR_MAP`은 ¥/€/元/RMB/위안/유로/JPY/엔을 통화로 인식하는데, `_to_number`는 그 기호를 못 벗겨 파싱 실패(`None`).
- 왜 취약: 통화기호 화이트리스트가 `_CUR_MAP`과 불일치. 괄호 음수 `(1,234)`·유니코드 마이너스·유럽식 `1.234,56`도 미처리.
- 영향/재현(실측):
  - `¥500` → `None`, `€10` → `None` (통화 금액 **행 전체 소실**)
  - `(1,234)` → `None` (회계식 음수 → 값 소실)
  - `1.234,56` → `1.23456` (유럽식 소수점 오해석 → 100,000배 오차)
- 권장수정: 기호 제거 목록을 `_CUR_MAP` 키와 동기화(모든 통화기호), 파싱 전 부호 감지(괄호/`△▲`/`−`), 천단위·소수 구분자 로케일 판정. 최소한 "숫자만 남기기" 후 파싱.
- 안전도: **결정필요** (음수·소수 표기 규약을 데이터 샘플로 확정 후)

### H2. `_to_number`(queries)가 괄호/△/▲/유니코드마이너스 음수 부호를 조용히 제거 (집계 파이프라인, 별도 구현)

- 권장수정: 부호 감지 후 정규화; extract쪽 `_to_number`와 **단일 구현으로 통합**.
- 안전도: **결정필요**
